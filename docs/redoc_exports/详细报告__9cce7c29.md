## Proposal 质量分析

### dl_lr_schedule

#### claude-opus-4.6

Opus 提出的研究问题极为宏大：以字符级语言模型（character-level LM）为切入点，系统比较 warmup+cosine、SGDR、1cycle 等调度策略，并通过 Hessian trace、gradient noise anisotropy 等动力学指标从理论上解释性能差异。典型 proposal（sample_15）提出了"曲率门控 warmup"（curvature-gated warmup）——根据训练初期 Hessian trace 幅度自适应延长 warmup 时长，以及在最后 10% 训练时间追加的尾部 cosine restart。这是一个真实的研究想法，超越了"warmup+cosine"的简单描述。

其他样本（sample_00、sample_04、sample_07、sample_10、sample_17）同样呈现出丰富的想法，包括：

- 三阶段混合策略：warmup → SGDR 探索（多个 cycle）→ 单调 cosine 收敛（多个样本）

- CRAC（Curvature-Responsive Adaptive Cycle）：用 sigmoid 函数将 Hessian 代理值映射为循环振幅，模拟曲率自适应调度（sample_04）

- 高 LR 探索平台期（plateau）+ cosine 衰减（sample_17）

这些 proposal 从研究价值角度看具有一定新颖性——它们均试图将 loss landscape 理论与实际调度设计挂钩。但共同缺陷是：**任务背景理解错误**。所有 opus proposal 都把研究场景定位为"字符级语言模型（character-level LM）"，而实际评测任务是 ResNet-20/CIFAR-10 图像分类。Proposal 与实际任务之间存在根本性的场景错配。

#### qwen25_7b base

Base 模型的 proposal 结构较为简略，通常停留在 approach 部分的高层描述层面，缺乏数学推导和理论依据。典型样本（sample_01、sample_06、sample_15、sample_16）的研究方向仅是：

> "实现以下 LR schedule：warmup-then-cosine decay、SGDR、1cycle，在字符级语言模型上比较效果"

内容基本是对任务描述的复述，没有原创性的设计决策。但对最终任务而言，这反而有利：worker 在没有明确复杂约束的情况下，更容易按照自身先验实现标准的 warmup+cosine 或 SGDR，从而达到较高分数。

**典型差异对比：**

| 项目 | claude-opus-4.6 | qwen25_7b base |
| --- | --- | --- |
| 研究深度 | 提出具体参数化（Hessian proxy、sigmoid gate、curvature threshold） | 仅列举调度名称 |
| 场景对应 | 场景错配（以字符级 LM 为背景） | 同样错配，但影响更小（proposal 太简单，worker 自行决定） |
| 实现可操作性 | 提案复杂，worker 难以直接转化为正确代码 | 提案简单，worker 有较大自由度 |

### dl_activation_function

#### claude-opus-4.6

Opus 在激活函数任务上提出了雄心勃勃但与任务完全脱节的研究方向：**联合谱传播理论**（CANIO: Coupled Architecture-Normalization-Initialization-Optimization Co-Design）——推导 mean-field 理论下的前向/反向 Jacobian 谱如何联合依赖于架构拓扑、归一化、初始化和优化器，并设计"谱耦合条件"（spectral coupling condition）来指导激活函数的选择。

这些提案论述严密、有明确的理论框架，但全部聚焦于系统级的架构/初始化/训练动力学联合设计，而非激活函数本身的设计。当 worker 被要求实现 approach 中描述的方案时，只能从这些宏大框架中提取出最简单的可实现组件：learnable-beta Swish（x * sigmoid(β * x)）——因为这是最接近"联合可学习参数"概念的东西。

**20 个样本的实现几乎一致：**

- 15 个样本：x * sigmoid(self.beta * x)（learnable Swish）

- 3 个样本：x * tanh(F.softplus(x))（Mish，无可学习参数）

- 少数样本尝试了 ELU（sample_04）、ELU+Swish 混合（sample_11）、learnable alpha Swish（sample_03）

没有任何样本尝试真正新颖的激活函数结构。

#### qwen25_7b base

Base 模型的激活函数 proposal 同样停留在高层系统描述层面，但 worker 实现的多样性略高：

- 12 个样本：learnable Swish（x * sigmoid(β * x)）

- 5 个样本：Mish（x * tanh(softplus(x))）

- 1 个样本：learnable GELU+Mish 混合（sample_17）

- 1 个样本：learnable GELU+SiLU+Mish 三路混合（sample_07）

- 1 个样本：带归一化门的 Swish（sample_10，gate = sigmoid(β * x / std(x))）

Base 模型实际体现出了比 opus 稍多的实现多样性，但两者都没有真正发明新激活函数，都在已知激活函数（Swish、Mish、GELU）的组合空间内打转。

**核心问题：** 激活函数任务的本质是"发明一个比 ReLU 更好的激活"，而所有提案都没有从激活函数设计空间出发，都选择了已知且被证明有效的函数，缺乏真正的创新。

### cv_data_augmentation

#### claude-opus-4.6

Opus 在数据增强任务上提出了 **joint augmentation-architecture co-search** 框架（如 JAAC、JAANA 等），核心思想是将增强策略和网络架构联合优化，并引入频谱域 Jacobian 正则化、PAC-Bayes 泛化界等理论工具。部分样本（sample_02、sample_05）甚至实现了真正的自定义 transform：

- **FrequencyBandDrop（sample_02）**：在频域随机置零高频分量，或随机扰动相位，鼓励模型依赖低频特征（得分 92.07%）

- **手写 AugMix + FrequencyDomainMask（sample_05）**：实现 AugMix 混合逻辑，叠加频域掩码（得分 92.55%）

这是 6 个 run 中唯一出现了真正原创实现代码的情况。然而这些实现的精度反而更低——过于激进的频域扰动损害了训练稳定性。

其余样本（约 75%）均实现了标准的 RandAugment + RandomErasing 或 AutoAugment + RandomErasing 组合，与提案的宏大框架几乎没有对应关系。

#### qwen25_7b base

Base 模型的增强 proposal 同样是高层 NAS+增强联合优化描述，但 worker 几乎全部实现为标准管道：

**全部 20 个样本基本相同（代码如下）：**

```python
transforms.RandomCrop(config['img_size'], padding=4)
transforms.RandomHorizontalFlip()
transforms.RandAugment(num_ops=2, magnitude=9)  # 或 AutoAugment
transforms.ToTensor()
transforms.Normalize(config['mean'], config['std'])
transforms.RandomErasing(p=0.5, scale=(0.02, 0.33), ratio=(0.3, 3.3))
```

没有任何样本尝试自定义 transform、mixup/cutmix、频域增强等更激进的方法。高度一致，等同于 worker 的默认先验。

## Worker 忠实度分析

### 整体规律

通过系统比对 proposal 的 approach 与 editable_region.py，可以得出以下结论：

**Worker 对 proposal 的执行策略：** 当 proposal 描述的是高层研究框架（"联合优化架构和增强策略"）而没有给出具体参数时，worker 会退化为其自身先验——即标准的 warmup+cosine（LR 任务）、learnable Swish（激活任务）、RandAugment+RandomErasing（增强任务）。

### dl_lr_schedule 典型对照

| 样本 | Proposal 核心要点 | 实现内容 | 忠实度 |
| --- | --- | --- | --- |
| opus sample_15 | 曲率门控 warmup + single-cycle cosine + 尾部 cosine restart | warmup(5%) → cosine(85%) → restart(10%) | **基本忠实** |
| opus sample_04 | CRAC：sigmoid 映射 Hessian proxy → 循环振幅 | 实现了完整的 CRAC 逻辑，包括 sigmoid gate | **高度忠实** |
| opus sample_00 | warmup → 3-cycle SGDR → cosine 收敛 | 实现了三阶段 warmup+cycle+decay | **较为忠实** |
| base sample_01 | "比较各种 schedule，warmup+cosine 为基线" | 简单的 5-epoch warmup + cosine decay | **实现了最简版** |
| base sample_06 | approach 字段为空 | 标准 warmup+cosine | **Worker 默认先验** |
| base sample_11 | "使用 SGDR：两个递增周期" | 2-cycle SGDR，第二次从 base_lr*0.5 重启 | **忠实** |

**关键发现：** Opus 的 worker 忠实度实际上相当高——CRAC、尾部 restart 等复杂细节都被正确实现。然而 opus proposal 的整体框架（为字符级 LM 设计）与实际任务（ResNet-20/CIFAR-10）不匹配，导致即使忠实实现也可能选择了对视觉分类并不最优的调度形状。

### dl_activation_function 典型对照

| 样本 | Proposal 核心要点 | 实现内容 | 忠实度 |
| --- | --- | --- | --- |
| opus sample_03 | 谱耦合激活：learnable alpha 控制 Fisher 矩阵条件数 | self.alpha * x * sigmoid(self.beta * x) | **形式上忠实** |
| opus sample_04 | "近等距 Jacobian：f'(x)=1 正半轴" | F.elu(x, alpha=1.0) | **忠实（ELU 满足条件）** |
| opus sample_10 | 可学习的曲率自适应 ELU | learnable alpha 控制负半轴斜率的 ELU | **忠实** |
| base sample_07 | 联合优化框架（未给具体激活） | learnable weighted sum of GELU+SiLU+Mish | **Worker 自主选择** |
| base sample_17 | "GELU 和 Mish 的统一" | w * gelu + (1-w) * mish，learnable w | **对概念有所体现** |

### cv_data_augmentation 的系统性 Worker Prior

数据增强任务展现了最强的 worker prior 效应：

- Opus worker 在少数案例中尝试了自定义 FrequencyBandDrop、手写 AugMix（sample_02、sample_05），其余约 75% 使用标准管道

- Base worker **20/20 全部使用了相同的 RandAugment+RandomErasing 管道**，与 proposal 内容完全无关

这说明即使 proposal 描述了 NAS 框架，如果没有具体的 transform 参数，worker 会直接忽略并实现默认先验。

## 通过样本深析

### dl_lr_schedule opus sample_15（93.23%，PASS）

**Proposal 要点：** 曲率门控 warmup（5%）+ single-cycle cosine（85%）+ 尾部 cosine restart（10%，峰值 LR = base_lr * 0.05）

**实现：** 严格对应 proposal，warmup → cosine decay → tail restart，min_lr = base_lr * 0.001

**为何通过：** 实现确实来自 proposal 的具体设计，worker 忠实执行了三段式框架。得分 93.23% vs 阈值 93.01%，仅高出 0.22%。尾部 restart 带来了微小的额外探索，但也可能有随机因素。**结论：部分归功于 proposal 的明确设计，部分为随机。**

---

### dl_lr_schedule base 的 7 个通过样本

通过样本（sample_01、sample_06、sample_10、sample_11、sample_15、sample_16、sample_18）的实现：

| 样本 | 实现 | 得分 |
| --- | --- | --- |
| sample_01 | warmup(5ep) + cosine to min_lr=1e-4 | 93.26% |
| sample_06 | warmup(5ep) + cosine（min_lr=1e-4） | 93.12% |
| sample_10 | warmup + 2-cycle SGDR（40%/60% 拆分） | 93.07% |
| sample_11 | warmup + 2-cycle SGDR（base_lr → 0.5*base_lr） | 93.05% |
| sample_15 | warmup(5ep) + cosine | 93.09% |
| sample_16 | warmup(5ep) + cosine | 93.10% |
| sample_18 | warmup(5ep) + cosine | 93.06% |

**结论：6/7 的通过来自标准 warmup+cosine，这是 worker 的默认先验，与 proposal 的实际内容几乎无关。** 通过率 38.9% 反映的是 worker prior 的成功率，而非 base 模型提案的创新价值。

---

### dl_activation_function opus sample_03（93.31%，PASS）

**Proposal 要点：** 谱耦合激活，双参数 learnable Swish（learnable alpha 控制整体幅度，learnable beta 控制门控锐度）

**实现：** self.alpha * x * sigmoid(self.beta * x)

**为何通过（93.31%，仅高阈值 0.04%）：** 双参数 learnable Swish 可能在训练中自适应到了比单参数版本略好的形状，但优势极其微小。19/20 样本未通过，说明这更可能是随机性。**结论：Worker prior（learnable Swish 是当前激活函数的 SOTA 变体）+ 随机运气，proposal 的理论框架贡献有限。**

---

### cv_data_augmentation — 全面未通过分析

全部 40 个样本均未通过（阈值 93.87%，最高分 93.78%，差距 0.09%）。

失败原因：

1. **阈值极高**：CIFAR-10 上 ResNet-20 达到 93.87% 需要精细的参数调优

2. **Worker 实现趋同**：几乎全部使用 RandAugment(n=2, m=9) + RandomErasing，这是强基线但参数未必最优

3. **Opus 的激进尝试适得其反**：FrequencyBandDrop（92.07%）、手写 AugMix（92.55%）反而更低

4. **超参数才是关键**：正确的 RandAugment 参数（如 n=3, m=15）才可能突破阈值，而 proposal 对此无指导

## 结论与启示

### (a) base 模型 vs opus 的 Proposal 质量

**表面上 base 通过率更高（38.9% vs 5%），但这不意味着 base 的 proposal 质量更好。**

- **Base 模型的 proposal 内容更简单、更空洞**，导致 worker 有更大自由度使用默认先验，恰好命中了最优实现

- **Opus 的 proposal 更复杂、更原创**（CRAC、谱耦合激活、频谱增强），但存在根本性的任务场景错配（全部以字符级 LM 论文集为背景），且复杂的设计被 worker 忠实实现后未必适合 ResNet-20/CIFAR-10

这是典型的**"研究叙事过拟合"**问题：with_research_question 策略下，research question 的背景（字符级 LM 论文集）强烈影响了 proposal 的场景设定，使得生成的设计与实际评测任务脱节。

### (b) Fine-tuning 效果的判断

从本次 6 个 baseline 结果来看，**尚未能直接判断 fine-tuning 效果**，因为这 6 个 run 均属于 baseline 条件（opus API 直接推理 vs qwen25_7b base 推理），不涉及经过 RL 微调的 checkpoint。

但本次结果进一步证实了前一版评测的核心结论：**base 模型在 with_research_question 策略下的通过率主要来自 worker prior，而非真正学会了给出可执行的创新设计。** Fine-tuned checkpoints 需要在 proposal 中给出明确的参数化设计，才能超越纯 worker prior 的成功率。

### (c) 需要改进的方向

1. **任务背景对齐（最关键）：** Proposer 接收到的 research context 是字符级 LM 论文集，导致 opus 场景错配。需要在 prompt 中明确提示 proposer 关注实际执行任务的上下文（ResNet-20/CIFAR-10 图像分类），而非仅仅 research paper 的主题。

2. **Proposal 可操作性：** Opus 的高质量理论 proposal 缺乏具体超参数（曲率阈值、频域 band 宽度等），导致 worker 只能近似实现。需要引导模型在 proposal 中给出更多具体的可执行参数。

3. **激活函数任务的创新缺失：** 两个模型都没有真正提出新的激活函数，都在 Swish/Mish/GELU 空间内微调。需要引导模型探索更宽泛的设计空间，例如分段线性族、polynomial 激活等。

4. **数据增强阈值过高：** 93.87% 的阈值对 ResNet-20/CIFAR-10 来说极具挑战性，标准 RandAugment 管道最高只达到 93.78%。后续可考虑降低阈值，或增加允许 worker 调整超参数的机制。

5. **评测解耦 Proposal 贡献：** 当前 pass rate 混合了 worker prior 和 proposal 的贡献，无法精确衡量 proposal 的有效性。建议增加对比实验：固定 worker 实现标准先验，对比 proposal 引导下的 worker 实现差异，量化 proposal 的真实增量价值。
