Start where I always start: don't trust a single metric. ARI and NMI are great, but they can lie. If a method produces more clusters than the true ground truth, the ARI can still look decent — the score is contaminated by label count mismatch. That's the whole game. So the honest question isn't 'which method is best' — it's 'how do I make the comparison fair and information-rich?' I want to design an experiment that forces the methods to compete under conditions where their weaknesses are exposed, not hidden.

Why blobs are the wrong default: they are the *easiest* dataset, the one where every method looks good. A method that shines on blobs is likely overfitting the toy case. So the evaluation setting is deliberately artificial and high-variance — a single Gaussian blob, no noise, no structure. Under that, the weakest method is likely K-Means, because it's a rigid convexity assumption on a convex shape. That's not a criticism of K-Means — it's a feature: if K-Means is rigid, then it *fails* on non-convex data, and *exactly* when I need it most. So I'm not trying to beat K-Means here; I'm trying to *test* whether my idea can survive this artificial-but-strict setting.

Now the leap. The standard move is to add a parameter: a distance metric or a connectivity graph. But adding a parameter is a recipe for overfitting the evaluation itself — the same blob, same `eps`, same everything, and I just choose the metric that looks best. That's cheating. Instead of adding a knob, I want to *embed* a knob into the data. Embedding turns the method into a function of the data: the decision rule is data-dependent, not model-dependent. So the idea is: transform the feature space into a *higher-dimensional space* (using an embedding) so that the data's intrinsic structure becomes a *local* geometric property, and then cluster it in that space. Convex clusters become easy in a space where they are linearly separable; non-convex clusters become separable by a local metric; and in high-dimensions, an embedding can reduce the impact of dimensionality on distance. The embedding itself is the knob — it's a data-derived decision rule, not a parameter I tune.

Why this cuts against consensus: most clustering research treats the embedding as a fixed pre-processing step. I'm claiming the opposite — the embedding is *part of the clustering algorithm*, chosen by the data, and its quality is what determines cluster quality. That reframes the problem from 'design a better metric' to 'design a better data space.' And here's the non-trivial crux: the embedding must be *learned* end-to-end, not pre-computed, because if I fix the embedding once and reuse it for all datasets, the learned embedding for blobs is useless for moons. The embedding is a function of the data, so it has to be re-learned per dataset. That's why I need a custom distance function that accepts the embedding as a fixed *input* argument — the distance is then a composition of the learned embedding and a local geometric kernel. The decision rule is: a point belongs to a cluster if it is close to the cluster's embedding in the learned space, and close is defined by a distance that decays with inter-peak distance — a local Gaussian kernel. This makes the embedding and the clustering co-evolve.

How I keep myself honest: the decision rule is falsifiable on the artificial blob dataset. If the method fails to beat K-Means on a single clean Gaussian (no noise, no structure), then the embedding did not *embed* the data well and I reject it, not the metric. The honest baseline is K-Means on the raw data, because K-Means is the default and its failure on blobs is exactly the case I'm trying to exploit. If the embedding doesn't help on blobs, it's not worth the complexity; if it does, then I run it on the harder datasets (moons, varied-density, digits) and check whether the gains hold — and I'll report the raw numbers, not cherry-picked ones. If it only helps on blobs and not elsewhere, I've overfit the evaluation and should not claim generalization.

Core idea: Make the clustering algorithm data-derived by embedding the feature space into a learned higher-dimensional space, so that the decision rule (a local Gaussian kernel over the embedding) is geometry-dependent and thus able to handle convex, non-convex, and high-dimensional data — and keep the embedding re-learned per dataset so it's not a fixed pre-processing step.

Non-trivial crux: The embedding must be learned end-to-end per dataset (not a fixed pre-computation), and the decision rule is a local Gaussian kernel over the embedding — otherwise the embedding is not a knob but a knob you tuned on the very same evaluation, which would be overfitting.
