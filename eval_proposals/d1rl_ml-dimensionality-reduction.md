Let me start not from an algorithm but from what MUST be true about the embedding. The evaluation is kNN accuracy, trustworthiness, and continuity — all metrics about *neighborhood relationships*. So my invariant is: if I can preserve neighborhoods, I preserve the data's structure. The honest question is, can a linear method preserve neighborhoods at all? PCA is a linear projection. By construction it maps linear subspaces. But a neighborhood is a *local* notion — a circle in the original space, a sphere, a manifold. Linear subspaces are globally flat, so they cannot bend to follow a local structure. That's not a theorem I proved, it's a deduction from the definitions. Therefore the entire field of nonlinear dimensionality reduction is justified by this deductive gap, and any real improvement MUST come from nonlinear methods.

Now the part that cuts against consensus. The standard story is "nonlinear methods are slow, nonlinear methods are clever." I refuse to accept that dichotomy as given. The consensus moves are: t-SNE (local, gradient descent, slow), UMAP (local, fast, but still gradient-based), Laplacian Eigenmaps (local, slow), Isomap (global, slow). Each of these is "fast enough" in a different regime, but none are fast enough for the CPU-bound case we're given (n_samples <= 5000, n_features up to 784, under 5 minutes). The time constraint is the real constraint here — it's not a research constraint, it's an engineering constraint. If I can't make a method fast enough to run in 5 minutes on CPU, I haven't solved the problem, I've only found a toy.

So the transfer I want to make is not from theory to code but from *another subarea of ML*: optimization in the form of coordinate descent, the way gradient-free algorithms (coordinate ascent / descent, coordinate-wise optimization, alternating minimization) are used in EM, in sparse regression, and in graph learning. Coordinate descent has two virtues that map directly onto my requirements:
- It is *gradient-free*, so it can operate in a setting with no gradient — the high-dimensional space of embeddings. (This is why it's the right tool, not a coincidence.)
- It is *parallelizable across samples*, so the per-iteration cost is O(n_samples) and it can be batched. This is the whole thing — a per-iteration cost that is linear in samples, run in parallel, means the wall-clock scales as n_samples rather than n_features. That is exactly the difference between "I can't run it" and "I can run it in 5 minutes." And since the embedding is the only thing that matters, and the embedding is the only thing that is stored, this is the kind of trade I want: pay in elegance, get in speed.

The leap is to recognize that preserving neighborhoods is a *constraint satisfaction problem* — the embedding must satisfy that a point's neighbors in the original space map to its neighbors in the embedding space. That framing is not decorative; it tells me the right mathematical object is a *graph* whose edges encode "should be close." And the natural solver for a graph with a gradient-free objective is coordinate descent: fix all but one embedding, minimize a local loss over that coordinate, and repeat. The loss is a distance penalty — push neighbors closer, non-neighbors farther — and it has the property that the objective is separable across coordinates, so coordinate descent is justified by the separability, not by any clever trick.

Why this cuts against the field: everyone treats dimensionality reduction as a "find the axes" problem. I'm treating it as a "reconstruct the graph" problem. The method is not a new algorithm; it's the coordinate-descent graph optimizer from another area repurposed to dimensionality reduction. That's the crux — the whole thing is a transfer, and the transfer only pays off because of the specific evaluation and the specific constraint (neighborhood preservation, fast on CPU), not because the coordinate-descent solver is intrinsically good.

Now the non-trivial crux that would sink this if I'm not honest: the convergence of coordinate descent is NOT guaranteed, and it can easily converge to a *local* optimum that is a bad embedding. So I must ship a *fallback* — not an excuse, a safety net. The fallback should be an *existing* method (t-SNE or UMAP) run once, and its embedding should be used only when coordinate descent fails or produces a clearly inferior result. The decision rule is: if the coordinate descent embedding's trustworthiness and continuity scores are not clearly better than the fallback, prefer the fallback. This is not a heuristic I add — it's a *formal* fallback: if the local optimum is not provably better, the global optimum is not what we ship. The evaluation is the litmus test, not the proof.

One more deduction I refuse to drop: since the embedding is the only thing that matters, the method is defined by what it returns, not by how many hyperparameters it has. So I deliberately keep the interface simple — only `n_components` and `random_state`. Any knob I add that doesn't clearly improve the embedding on the diverse datasets is a complexity tax, not an advance.

**Core idea:** Treat dimensionality reduction as a neighborhood constraint problem and solve it with coordinate-descent graph optimization (gradient-free, parallelizable across samples, so fast on CPU), with a fallback to an existing method if coordinate descent converges to a bad local optimum.

**Non-trivial crux:** The coordinate-descent embedding is a local optimum, not a global one, so a fallback embedding (t-SNE/UMAP) must be shipped as a formal fallback — prefer the fallback over coordinate descent only when its scores are clearly better, since a non-robust local optimum is worse than a fallback even if the fallback is suboptimal.
