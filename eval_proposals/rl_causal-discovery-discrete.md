Let me start from the honest constraint I keep returning to: discrete data with varying cardinalities. Continuous-variable methods like PC or FCI assume Gaussianity; they won't even ingest my inputs. So any promising continuous trick is ruled out immediately. That's not a deficit of the data—it's the method's ceiling. The field's reflex is to discretize continuous data; here the opposite holds—discretization is baked in, and I should lean into it rather than fight it.

Now, where does the failure live? When I run vanilla constraint-based search (e.g., MMPC/PC for skeleton and v-structure identification), it gets stuck on low-sample regimes and high-cardinality variables. Why? Constraint-based tests rely on conditional independence decisions. For discrete variables, the default is chi-squared or mutual information, which both suffer under small sample counts relative to variable cardinality: chi-squared's asymptotic guarantees don't kick in, and mutual information estimates become noisy. The decision rule becomes brittle, and false negatives (missing edges) proliferate.

So let me not reach for a fancier score; I want to change the *mechanism* of the test itself. The mechanism that breaks is the *conditional independence* check. What if I replace it with something that doesn't require a large sample to be reliable?

Here's the leap: treat each variable as a *classifier*. Consider a candidate edge X → Y. Instead of asking "are X and Y conditionally independent?" ask "can I predict Y from X given its parents?" This flips the paradigm from an indirect statistical test to a direct predictive one. Classifier quality becomes my CI proxy. The non-trivial part is picking the classifier. A linear/logistic model would be wrong—my variables are discrete with different cardinalities. Decision trees fit naturally: they split on categorical features and can handle varying cardinalities. Plus, tree-based importance gives me a ranked ordering of parents, which is exactly what I need to build the skeleton and orient edges.

But there's a hidden danger I want to make explicit before I declare victory: decision trees can overfit. If I use the same data to train the tree and then read off its importance, I'm effectively using the data twice, inflating my confidence. That's the same overfitting trap that haunts every ML pipeline that treats the same data as both training and validation. The fix is to split the data into two halves: one for training the tree, one for reading off the importance. This cross-validation-style separation cuts the overfitting risk.

One more thing I should check: since I'm now doing prediction instead of testing, I inherit a different kind of bias—predictive accuracy may not align perfectly with causal faithfulness. So I'll keep the faithfulness assumption intact and only use the classifier as a CI *proxy*; if a node's predictive power collapses when conditioned on a set, I treat it as conditionally independent. That keeps the causality semantics honest while borrowing the robustness of the classifier.

Core idea: Replace the constraint-based conditional independence test with a decision-tree classifier: train a tree to predict each variable from its neighbors, and use feature importance to rank parents, treating low-predictive-power as conditional independence.

Non-trivial crux: The classifier must be discrete-friendly (decision trees fit this), and the decision rule must be split into separate training and validation sets to avoid overfitting; otherwise the proxy CI test can be overly confident.
